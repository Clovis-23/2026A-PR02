# Fiche de décisions

Cette fiche explique les choix présents dans notre projet de prédiction des points NBA. Les autres options servent à expliquer les compromis ; elles ne représentent pas une comparaison expérimentale et l'équipe doit confirmer celles qu'elle avait réellement envisagées. Les validations et leurs dates restent à renseigner à partir des échanges réels avec l'auxiliaire.

| Choix | Options envisagées | Choix retenu et justification | Validé par l'auxiliaire (date) |
| --- | --- | --- | --- |
| Domaine et jeu de données | Statistiques sportives individuelles ou résultats d'équipes ; données sur un match ou sur une saison. | **Statistiques de joueurs NBA par saison.** Le basket donne un contexte concret pour interpréter les résultats. Le tableau contient plusieurs caractéristiques numériques et une catégorie, le poste, ce qui permet de traiter les deux types de saisie demandés. Le fichier utilisé est `nba_joueur_saison_2005_2024.csv`. La source exacte et sa licence restent à confirmer dans le README. | Validations A et B : à renseigner. |
| Préparation des données | Garder toutes les observations du fichier brut ou sélectionner une période et un minimum de matchs ; attribuer un numéro aux postes ou créer une colonne par poste. | **Garder les saisons NBA à partir de 2005 et les joueurs ayant au moins 20 matchs.** Le minimum de matchs limite la présence de moyennes calculées sur très peu de rencontres. Nous gardons les colonnes utiles et renommons celle des minutes. Avec `get_dummies`, chaque poste devient une colonne de 0 et de 1 : cela évite d'imposer un ordre artificiel entre les postes. | À renseigner. |
| Variable cible et type de problème | Prédire une valeur numérique ou classer les joueurs dans des groupes de performance. | **Estimer `pts`, les points par match, par régression.** Cette cible est numérique et facile à comprendre pour l'utilisateur. Les entrées décrivent la même saison : l'application estime une moyenne à partir d'un profil statistique, sans prétendre prévoir exactement le prochain match. | Validation C : à renseigner. |
| Modèle | Régression linéaire, arbre de décision, forêt aléatoire ou k plus proches voisins. | **Régression linéaire.** Elle fournit une première solution simple, rapide à entraîner et assez facile à expliquer. Les statistiques comme les tirs tentés et les minutes ont un lien plausible avec les points. Un arbre ou une forêt pourrait représenter des relations plus complexes, mais ajouterait des choix de réglage. Nous n'affirmons pas que la régression est le meilleur modèle : c'est celui implémenté pour ce projet. | Validation C : à renseigner. |
| Métrique et référence | MAE, RMSE ou R² ; prédiction constante ou modèle appris. | **MAE, comparée à une référence qui prédit la moyenne des points de l'entraînement.** La MAE exprime l'erreur moyenne en points par match, donc dans une unité directement compréhensible. La RMSE pénaliserait davantage les grandes erreurs. La référence permet de vérifier si le modèle apporte quelque chose par rapport à une estimation constante. Le calcul de la MAE est aussi vérifié avec NumPy. | Validation C : à renseigner. |
| Séparation des données | Séparation aléatoire, séparation par année ou validation croisée. | **80 % pour entraîner et 20 % pour tester, avec `random_state=42`.** Cela réserve des observations à l'évaluation et permet de retrouver la même séparation. Une séparation par année conviendrait mieux à une étude de prévision des saisons futures. La séparation actuelle ne garantit pas qu'un même joueur soit absent de l'autre ensemble lorsqu'il a plusieurs saisons. | À renseigner. |
| Interface graphique | Streamlit, Tkinter ou une autre bibliothèque d'interface. | **Streamlit en local.** Ses champs numériques, listes de choix et boutons permettent de construire rapidement le formulaire. Il affiche aussi les tableaux et les figures Matplotlib. Ce choix nous laisse du temps pour le modèle, la validation des valeurs et l'historique. | Validation D et maquette : à renseigner. |
| Sauvegarde et historique | Réentraîner au démarrage ou charger un modèle enregistré ; paramètres du formulaire écrits dans le code ou stockés séparément. | **Modèle dans un fichier joblib, métadonnées dans un JSON et historique dans un CSV.** L'interface charge le modèle existant au lieu de le réentraîner. Le JSON fournit les catégories et les bornes des champs. Le CSV conserve les profils saisis et les prédictions pour les consulter ensuite. | À renseigner. |
| Organisation et tests | Regrouper tout dans un script ou séparer les responsabilités ; vérifier seulement dans l'interface ou tester la logique. | **Modules séparés pour les données, le modèle, les variables, les exceptions et l'interface.** Les deux classes de variables appliquent chacune leur validation. L'application contient une instance du modèle. Les huit tests pytest vérifient des cas usuels, des limites, des erreurs et le calcul de la MAE. Ils facilitent la détection d'un problème sans lancer toute l'interface. | À renseigner. |

Les résultats chiffrés, les limites du modèle et les commandes de lancement figurent dans le [README](README.md). L'aide reçue de l'IA et les vérifications associées sont décrites dans le [journal d'IA](JOURNAL_IA.md).
